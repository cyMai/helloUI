# helloUI

给长期迭代的前端 demo 用的 Codex skill。项目以**可运行 demo 和用户持续提出的需求**为依据；不要求原型图。helloUI 帮助你从现有实现建立可延续的规则，重点解决：

1. 同一页面的多个模块、不同功能页面之间，风格和同义组件保持一致。
2. 导航、组件行为、校验、格式化和数据处理等逻辑能在合适的层级复用。
3. 同一功能页面用一份 HTML/路由适配网页端和手机端。

helloUI 不提供固定的视觉模板。用户的新需求决定本次要实现什么；当前 demo 说明项目实际做到了什么；`DESIGN.md` 记录已确认且仍有效的项目规则。三者冲突时先核对，再修改实现或规则，不把旧页面当成不可改变的标准。

## 安装

```bash
npx skills add cyMai/helloUI -s hello-ui -g -y
```

安装后开启新的 Codex 会话，使用 `$hello-ui`。附带的源码提取脚本需要 Python 3.9 或更新版本，无需额外 Python 包。

## 1. 新项目只有「页面参考.zip」

这里的 ZIP 是已有前端页面/demo 的打包文件，不是原型图。把它上传到 Codex，或放在当前工作区并告诉 Codex 文件位置。ZIP 可以包含 HTML、CSS、JS、图片和字体。直接发送：

```text
$hello-ui 我上传了「页面参考.zip」，里面是已有前端 demo 页面。请检查页面入口和资源，建立可运行的项目基线，保留原件。盘点页面、模块、共享风格、同义组件及重复的交互/数据处理逻辑；根据实际页面和我提出的需求建立一份简短的 DESIGN.md。无法确认的业务或设计意图标为 [待确认]。说明基线如何运行，以及哪些差异需要统一。
```

Codex 应按这条路径工作：

1. 检查 ZIP 内的文件和运行说明，确认它是可运行源码、静态 HTML 页面，还是资源不完整的导出文件；在工作区安全解压，保留原件与现有项目文件。
2. 识别页面类型、模块、共享 CSS/变量、组件、JS 行为和数据流。如果参考中的页面互相冲突，先列出证据，不把出现次数最多的样式自动当成正确规则。
3. 对静态 HTML/CSS 运行提取脚本，得到带文件位置的候选报告；再查看实际页面，确认可复用的规则和有意例外。
4. 在项目根目录建立**一份** `DESIGN.md`。它用六个视角记录当前有效规则：页面目标、业务语义（适用时）、体验、视觉、组件与交互、页面类型与布局。每节只写会影响后续开发的内容。

若 ZIP 没有完整源码，Codex 应说明缺失内容，并继续利用能看到的页面与资源建立基线；无法验证的结论写成待确认。若你只想分析参考、不想建立项目，可把提示里的“建立一个可运行的项目基线”改成“只分析，不修改项目”。

## 2. 进行中的项目用 helloUI 规范

在 Codex 中打开**现有项目目录**，直接调用 `$hello-ui`，不需要重新导入页面或另建项目。先区分两种情况：

还没有 `DESIGN.md`：让 Codex 读取现有页面、CSS、组件和交互代码，提炼项目当前实际使用的规则，核对页面表现后建立一份文档。它应标出不同页面之间的冲突和无法确认的设计意图，不把偶然重复的样式直接升级为规范，也不为了建文档大规模改写现有页面。

```text
$hello-ui 规范这个进行中的前端项目。先盘点现有页面、模块、共享样式、组件和可复用逻辑；检查实际页面，找出一致的规则与明显漂移。建立一份简短的 DESIGN.md，给出源码依据；无法确认的意图标为 [待确认]。先保留现有功能和页面结构。
```

已有 `DESIGN.md`：收到用户的新需求后，先读它并对照当前 demo，再实现新页面或模块。若文档与页面冲突，查清是新需求改变了规则、实现发生漂移，还是合理的页面例外；只修改受影响的规则和实现，不重写整份文档。

```text
$hello-ui 基于现有项目新增列表页和详情页。先读 DESIGN.md 与已有页面，沿用共享导航、按钮、卡片和排版；复用已有数据格式化与交互逻辑。每个功能页面都用同一份实现适配网页端和手机端。只在项目级规则真的变化时更新 DESIGN.md。
```

单页增加多个模块也可以直接描述任务：

```text
$hello-ui 在当前页面新增功能介绍、案例和 FAQ 模块。保持标题层级、模块间距、卡片和按钮一致；检查是否能复用现有组件与交互逻辑，并验证手机和桌面布局。
```

普通文案或局部样式调整不必每次调用 helloUI。新增页面、较大模块、共享交互，或发现跨页风格漂移时再用；只有项目级规则变化才更新 `DESIGN.md`。

日常迭代的顺序是：理解本次用户需求 → 查看受影响的现有页面与规则 → 复用或调整共享实现 → 运行 demo 并检查相关页面 → 仅在项目级规则改变时更新 `DESIGN.md`。页面截图可用于核对迭代前后的实际效果，不需要先制作原型图。

**逻辑复用**指相同职责使用同一实现，例如几个页面调用同一个表单校验、日期格式化或筛选函数。外观相似但业务含义不同的流程可以保持分开；纯 HTML 项目无需为了复用而引入框架。复用的实际代码入口可记在 `DESIGN.md` 的“组件与交互”节。

**跨端适配**指同一功能页保留同一份 HTML/路由，通过布局与交互适配不同宽度。首页和详情页可以是两个 HTML 文件；同一个详情页不需要另做 `detail-mobile.html`。完成后检查导航、内容顺序、主操作、横向溢出及共享组件在手机和桌面的表现。

## 一份 `DESIGN.md` 怎么写

一份文件按项目需要记录六个视角：

| 视角 | 记录什么 | 何时可省略 |
| --- | --- | --- |
| 页面目标与任务 | 用户、页面关系、关键任务、状态与验收点 | 目标不明时标 `[待确认]` |
| 业务语义 | 术语、对象、状态、校验与风险 | 纯展示 demo 无业务概念时 |
| 体验与内容节奏 | 字阶、密度、顺序、反馈与交互方式 | 只保留有实际约束的内容 |
| 共享视觉规则 | 颜色语义、字体、间距、形状与真实样式入口 | 不抄原始 CSS 清单 |
| 组件与交互 | 组件用途、变体、状态、共享逻辑入口 | 无跨页面复用时可写很短 |
| 页面类型与布局 | 页面壳层、模块组合和同页跨端变化 | 不虚构不存在的页面类型 |

写法见 [设计文档契约](references/design-contract.md)。`DESIGN.md` 是给下次开发看的当前规则，不是自动扫描报告。重要选择的理由可记在对应规则旁，日常改动无需增加文档。

## 自动提取能做什么

对已经解压到项目中的静态页面，可由 Codex 运行，也可以手动运行：

```bash
python /path/to/helloUI/scripts/extract_design.py --project-root /path/to/project
```

Windows PowerShell 示例：

```powershell
python 'C:\path\to\helloUI\scripts\extract_design.py' --project-root 'D:\my-project'
```

脚本在目标项目的 `.hello-ui/` 生成：

- `evidence.json`：页面、viewport、样式表、CSS 变量、重复声明、共享类名、媒体/容器查询、文件与行号。
- `proposals.md`：供人审核的候选规则与问题，如页面内局部样式、缺少 viewport 或固定宽度。

建议把 `.hello-ui/` 加入目标项目的 `.gitignore`。脚本只分析静态 `.html`、`.htm`、`.css`、`.scss` 文本；**不会判断 JS 逻辑是否值得抽取，不会计算浏览器最终样式，也不会创建或覆盖 `DESIGN.md`**。Codex 需要查看实际页面、核对源码与用户要求，才能确认规则。看不到的动态状态或视觉效果应明确标为未验证。

## 目录结构

```text
helloUI/
├── SKILL.md                         Codex 工作规则
├── README.md                        本说明
├── scripts/
│   └── extract_design.py            源码证据与候选规则
├── tests/
│   └── test_extract_design.py       提取脚本测试
└── references/
    └── design-contract.md           一份 DESIGN.md 的六个视角
```

开发此 skill 时可运行 `python -m unittest discover -s tests -v` 验证提取脚本。
