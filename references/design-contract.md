# `DESIGN.md`：一份当前有效的设计规则

默认在项目根目录维护一份简短的 `DESIGN.md`。它是 Agent 下一次开发页面时要读的入口，不是源码清单，也不是自动扫描报告。只记录能改变实现选择的规则，按项目需要保留下列部分；没有证据的部分不必填满。

## 项目范围与证据

说明覆盖哪些页面或页面类型、当前状态（已确认/从现有界面重建）、主要样式入口。把推断与已确认决定分开；无法判断设计意图时写 `[待确认]` 并给出核对对象。

## 共享视觉规则

写语义颜色、字体层级、间距/密度、形状、图标和反馈的用途。引用项目中真实的 CSS 变量或组件，不把每个原始数值重复抄成第二套 token。一个值反复出现只是候选证据，不能单凭次数变成规则。

## 页面壳层与组件

写导航、容器宽度、页面区域、模块节奏，以及按钮、卡片、表单等复用组件的适用场景和状态。页面特例写适用范围和理由；新页面不能凭一张参考图另建一套产品风格。

## 同一页面的响应式行为

写同一 HTML/路由在手机、布局转换区和桌面如何安排内容顺序、栏位、导航及主操作。仅在源码或明确决定支持时写固定断点；描述变化的原因与对任务的影响。参考 [响应式契约](responsive-contract.md)。

## 例外与待确认

保留少量当前有效的例外和未决选择，附受影响页面与下一步。重大历史理由可链接决策记录；过时结论不作为并列的现行规则。

更新时先对照现有 `DESIGN.md`，只改受影响的规则。`.hello-ui/proposals.md` 与 `evidence.json` 是待审核的工作材料，不应整段复制进本文件。
