# `DESIGN.md`：一份文档，六个视角

项目根目录的 `DESIGN.md` 是下一次开发要读的当前规则。六个视角沿用旧版六份文档中有用的分类，但不要求六个文件，也不要求每节填满。只写会影响下一次实现选择的结论；注明适用页面、状态（已确认/从参考页推断/待确认）和真实代码入口。源码报告只提供证据，不能代替设计判断。

## 1. 页面目标与任务（原 `spec.md`）

说明目标用户、页面清单或信息架构、关键任务、主要状态和验收条件。一个页面有多个模块时，写清模块在任务链中的作用；多个页面之间写清入口与去向。没有产品需求支撑的目标标 `[待确认]`。

## 2. 业务语义（原 `domain.md`，按需）

只在项目确有业务概念时写术语、对象、状态、校验边界、敏感信息或不可逆操作。纯展示 demo 可以省略本节；不要从页面文案臆造业务规则。页面间相同概念使用同一名称和状态含义。

## 3. 体验与内容节奏（原 `craft.md`）

写字阶、信息密度、内容顺序、反馈和动效目的，以及会影响完成任务的键盘、触控和可访问行为。记录跨模块一致的体验原则，不抄所有视觉数值。

## 4. 共享视觉规则（原 `design.md`）

写语义颜色、字体、间距、形状、图标和层级的用途与实际 CSS 变量/样式入口。重复值只是候选证据；确认后才作为全局规则。页面例外需写适用范围和理由，避免新页面重新发明一套视觉语言。

## 5. 组件与交互（原 `components.md`）

列出真正需要跨页面或模块一致的导航、按钮、卡片、表单等：用途、变体、状态、内容边界和实现路径。相同交互流程、校验、格式化或数据处理的共享函数/模块也在此指出；只有职责相同且重复已经出现时才建议抽取。细节参考 [组件契约](component-contract.md)。

## 6. 页面类型与布局（原 `template.md`）

说明页面壳层、页面类型、模块组合、共享导航与内容容器。写同一 HTML/路由在手机、布局转换区和桌面如何调整内容顺序、栏位和主操作，以及断点的依据。不同功能页可以有不同布局，同义组件仍应遵守共同规则。参考 [响应式契约](responsive-contract.md)。

## 例外与待确认

仅保留当前有效的例外和未决问题，附受影响页面与下一步。重大历史理由可链接 [决策记录](decision-records.md)。更新时先读现有文件，只改受影响的规则；不要把 `.hello-ui/proposals.md` 或 `evidence.json` 整段复制进来。
